# 0017 — The export is a stored snapshot of every transaction

Status: Accepted · 2026-09-26 · Implements `docs/workflows/missing-invoice-report.md §9` and
`docs/architecture.md §12B` · Closes `docs/phases/phase-1.md` gap 5

## Context

Feature L makes the Excel file a business owner hands to their accountant. §9 and §12B already
fix what matters most: the file is built in the background, it is a snapshot, it links back
into the application and never to storage, and it is stored under the same rules as source
documents. Five questions were still open.

1. **Which rows?** §9 lists four kinds: matched, not found, needs review, and needing no
   document. The Phase 1 definition says "every transaction". The two readings differ for a
   transaction that has no requirement. Such a transaction is not always one that was judged
   to need no document. It may belong to an identification batch that failed, or it may be
   waiting on a Clarification Question. `0014` records that nothing persists "judged, none
   needed".
2. **What the file is written with.** The repository had no spreadsheet or zip library.
3. **What an export is in the database.** Nothing recorded one, and no state machine
   described one.
4. **Where the links point.** A spreadsheet is opened outside the application, so every link
   has to be absolute, and the application had no configured origin of its own.
5. **Expiry.** §12B says exports are "subject to expiry" but gives no policy. Storage
   deliberately has no delete.

## Options

**Rows.** One option was to include only transactions that have a requirement. That drops the
fourth kind §9 names, and it breaks the "every transaction" promise. The other was one row
per Canonical Transaction. The second leaves open how an unjudged transaction should read:
calling it "needs no document" asserts something the system never decided.

**Library.** exceljs writes and reads `.xlsx` and handles hyperlinks, dates and number
formats. write-excel-file is smaller, but it only writes, so tests could not open the file
they were checking. Hand-rolled SpreadsheetML over a zip library means owning a file format.

**Link origin.** A new environment variable would be one more thing to configure per
environment, and a wrong value produces links that silently lead nowhere. The other option
takes the origin from the request that asked for the export. `connect-gmail` already derives
its callback this way (`src/app/api/gmail/connect/route.ts`).

**Expiry.** Deleting after N days needs a number nobody has chosen, and it needs a delete in a
storage module whose whole guarantee is that automation cannot delete. The alternative is to
keep exports and record the question.

## Decision

1. **One row per Canonical Transaction.** Each row is placed with `bucketOf`
   (`src/report/summary.ts`), so the file and the report cannot disagree about a requirement.
   A transaction with no requirement reads **"No document identified as needed"**, or
   **"Waiting for your answer"** if a Clarification Question about it is open. It never
   reads "No document needed" unless the user said so (`NOT_REQUIRED`). A second sheet
   carries the report's §5 summary, so the file can be checked against itself.
2. **exceljs**, server-only. Tests open the generated bytes with the same library.
3. **A Reconciliation Export entity** (`reconciliation_exports`), with the state machine
   `GENERATING → READY | FAILED` (`docs/state-machines.md §7`). The database refuses a
   storage reference on anything that is not `READY`, and refuses `READY` without one.
   Something that is not `READY` therefore has no file to download, by constraint rather
   than by convention.
4. **The link origin comes from the requesting request.** It is validated as a URL and
   carried in the event. Every document link is `<origin>/documents/<id>`, which is the
   document's page, not its bytes.
5. **Each request is a new export.** Generating never touches an earlier export's row or
   object. A `FAILED` export stays failed. Trying again means asking again, which produces a
   fresh snapshot of the state at that moment.
6. **Expiry is deferred** and marked OPEN DECISION in `docs/architecture.md §12B`.

## Why

An accountant reads the file as a claim about every payment. A row that says "no document
needed" for a payment nobody looked at is a false claim in the one artifact that leaves the
product. Stating what the system actually knows costs one extra phrase.

Taking the origin from the request means the link always points at the deployment that made
the file, with nothing extra to configure. The trade-off: the host header shapes link text in
the requester's own file, and only there. A link that leads somewhere wrong still reaches only
a sign-in page. It never reaches a document.

## Consequences

- **The snapshot is read in one Inngest step**, and the same step builds and stores the file.
  An infrastructure retry reads again, so the snapshot is of the state when the successful
  attempt began. That is still "the state at the moment it is generated".
- **An orphaned object is possible.** If the process dies between storing the file and marking
  the export `READY`, the stored object is referenced by nothing. The row stays `GENERATING`
  until `onFailure` marks it `FAILED`. The object is never served, and storage has no delete
  to clean it up. This is the same position as expiry, and it is resolved with it.
- **Links assume the user's active workspace.** `/documents/<id>` resolves the workspace from
  the session's active-workspace cookie. A user who owns two workspaces and follows a link
  while the other is active gets the same "not found" as anyone else. Revisit when multi-
  workspace owners are real. The fix belongs in workspace resolution, not in the export.
- Older exports stay downloadable by id. Only the latest is offered on the report.
